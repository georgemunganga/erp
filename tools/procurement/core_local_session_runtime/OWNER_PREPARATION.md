# Private Core local-session owner fixture source

`--prepare-core-session-owner-fixture` is a separate owner-side tool mode. It is unavailable without `P30_CORE_SESSION_OWNER_PREPARE=reviewed-private-only` and a protected 0600 `/evidence/core-owner-preparation-input.private.json`. It requires a **fresh** `proc_p30_core_session_20261024_01` clone in the private PostgreSQL 17 cluster, with tenant `p30-core-session-01`. It does not create a database, role, grant, HBA rule, or application host.

The input must be generated for the private cohort only, with random distinct actor IDs and passwords, main and foreign company/branch IDs, synthetic emails ending `@core-session.example.test`, and an independently captured pre-write owner-baseline SHA. The tool uses the existing Core `LocalPasswordHash.Hash` and `Verify` methods from the accepted HRM API assembly by exact reflection; there is no second password engine. It inserts two real Core role masters, two workerless LocalUsers, two explicit branch assignments, and the main/foreign companies and branches in one owner transaction. The granted actor has only `procurement-access`; the other has no action. It writes a protected row-write receipt, expressly marked **independent owner readback required**.

No real tenant, account, original StageB source database, or production database may be used. `--core-local-session-manifest` in the already compiled fbabe overlay can separately render the actual eleven-relation Core model manifest without opening a connection. Neither a rendered manifest nor this write receipt proves physical Core grants, actor authorization, or post-HTTP audit. The reviewed owner preparation profile must independently read back the new actors, current actions, branch scope, original rows, and audit baseline before promoting the Core HTTP plan. The Core HTTP runner retains the actual correct-secret login, wrong-secret PostgreSQL `28P01`, normal cookie flow, session revocation, and separate post-HTTP owner audit gates.

This source is **uncompiled and unexecuted**. It belongs to the isolated `codex/p30-core-session-owner-preparation` branch, separate from the frozen fbabe finite-login source and its accepted tool overlay.

`prepare_owner.py` is the separate guarded coordinator for the fresh Core01 clone and owner fixture. It requires an independently reviewed, hash-pinned plan, installed exact five-rule HBA, current role baseline, accepted StageB source catalog/data/ACL, actual model-derived Core manifest, and a compiled overlay with byte-identical accepted product DLLs. It uses the already reviewed StageB finite role/ACL helpers; all three new aliases are NOINHERIT LOGIN with SCRAM secrets generated in memory and stored only in protected output. The PostgreSQL owner connection is confined to the isolated private Unix socket. The runner pins its exact fresh output and never retries a partial clone or fixture. It captures the pre-actor data fingerprint, validates the two actor rows and Core role/branch/company graph through an independent owner SQL read, and leaves HTTP/owner post-audit unproven. The status remains unavailable until this source compiles, the physical grants are reviewed, and all private gates pass.
