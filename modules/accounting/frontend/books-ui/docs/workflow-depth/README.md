# Complete local workflow coverage

The current application registry defines **124 executable local flows** across Sales (28), Purchases (27), Banking (16), Accountant (14), Items & Projects (17), and Settings & Reports (22). `workflow-inventory.md` is generated from those definitions and records each ID, route, domain, ordered steps, fields, required inputs, effect, completion text, follow-ups and registry evidence label. `workflow-inventory.json` contains the corresponding typed definitions.

The flows are deliberately grouped around shared canonical screen families instead of duplicating a page for every action. A searchable Workflow Library, per-module workflow entry points and existing-record detail actions all lead to the same reviewable step engine. Successful completion creates/updates fictional browser-local records or artifacts, histories and links, and returns a receipt with next actions.

`engine-test-results.json` is produced by `scripts/test-workflow-engine.mjs`. It executes every registered flow and requires each one to change an operational local entity/artifact in addition to producing its receipt; it also checks negative prerequisites and money/status cases, derived totals, receipt routing and inventory import mapping. `tests/workflows.spec.ts` exercises the same per-flow completions in a browser along with cancel/validation preservation, responsive/mobile navigation, routes, client errors and outbound-request detection.

This is a materially complete interaction prototype, not a connected Zoho Books client or accounting engine. Local status/payment/journal/banking actions are simulations; they do not message, pay, approve, reconcile, post to or change the user's real tenant. Registry labels are implementation provenance only: the detailed local test suite does not verify that those workflows were inspected or completed in Zoho. The tenant map and screenshot limitation remain in `../verified-screen-patterns.md`, `../reference-manifest.json`, and the ignored action log.
