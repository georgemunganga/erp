# M6 principal invoice matching: source audit and implementation boundary

Source checkpoint: ERP `e03ac9735379b35f789d9e900fe849d7ab02f1f1` (merged M5d). This plan is source-only. No M6 migration, feature activation or business command has run.

## Existing contracts that can be retained

- `InvoiceMatchingFoundation` has deterministic two-way and three-way comparison, exact decimal arithmetic, tolerance and cumulative quantity/value checks. `InvoiceMatchExecutionEvidence` validates owner checkpoints and qualified claims. Existing invoice intake, original-document review, command receipts, exceptions, audit and outbox remain the owners of their respective records.
- Mapping and compare routes already require explicit Core permissions and keyed commands. `InvoiceMatchMappingVersion.IdentitySchemaVersion=2` supports a workerless Core principal; this is **actor identity**, not an M5 source-schema marker.
- `IInvoiceHistoricalExposureOwner` is registered as `UnavailableInvoiceHistoricalExposureOwner`. The fallback original-unit reviewer is also unavailable, though the retained unit-review route can provide a real review. A matching policy or an empty allocation table cannot turn either default into authority. Procurement can implement its own history owner; Finance posting is a separate concern.
- The matching flag is default-off. Current readiness depends on the legacy receiving schema and existing matching tables. Production has not accepted M6 source/owner readiness.

## Concrete M5 integration gaps

1. `ProcurementReceivingInvoiceProjection.InvoiceEvidence` and both selectors call the legacy receiving loader and filter legacy goods/service rows with `ExecutionVersion=1`. M5b accepted facts are `PrincipalReceivingSourceState` and `PrincipalReceivingFact` with a separate typed payload and sequence.
2. `InvoiceMappingLine` and projected `InvoiceMatchDocumentLine` can name only `GoodsReceiptLineId` or `ServiceAcceptanceId`; `InvoiceMatchAllocation` can bind only the legacy `ReceivingSourceStateId` and legacy acceptance IDs. Treating an M5 fact UUID as one of these IDs would bypass ownership FKs and change v1 JSON semantics.
3. M5d return drafts are proposal-only. No approved return effect exists that can safely populate `ReturnedQuantity`/`ReturnedNetAmount` for M5 accepted facts. A draft must not reduce physical acceptance or replenish billing capacity.
4. Qualified claims are impossible under the installed default historical exposure owner. `CompleteHistory` deliberately refuses an incomplete checkpoint and owner/local overlap. An internal owner must have an explicitly reviewed baseline covering pre-M6 invoices, claims, credit/handoff/status and manual-payment records; it must read every later relevant row under the comparison transaction. Replacing it with a local-only count would be an unauthorized completeness claim.
5. The current matching result and mapping receipts are versioned but their retained v1 JSON bytes/hashes must stay unchanged. An optional property on the old record without a dedicated codec would risk rewriting them.
6. `InvoiceRetainedUnitReview.VerifyOwnedProof` independently calls the legacy mapping verifier. The Core unit-review sealer and comparison consumer must dispatch to the new source-schema verifier together; a route-only change cannot complete independent review.

## Smallest coherent release slice

One new M6 source variant on the existing invoice matching routes: typed M5 issued revision plus M5 accepted fact mapping, current Core original-unit review, two-way/three-way evaluation, blocked results and exceptions, and qualified claims **only** when a Procurement historical exposure owner returns a complete, current, independently reconciled checkpoint. The source variant remains default-off until its schema, roles, policy, unit-review and owner gates all pass. The owner implementation and overlap protocol are part of the slice, not a later optional enhancement. Finance posting is explicitly out of scope.

The release may be built in smaller reviewable PRs, but no PR by itself is labeled M6 complete:

1. Typed source projection and pure tests (no write flag): M5a issued graph, M5b fact chain/payload digest, exact acceptance quantity/value and kind, no M5d proposal effect. Retain legacy v1 loader unchanged.
2. Schema and codec: add a distinct mapping payload schema for M5 facts, explicit source-schema marker independent of actor schema, typed principal fact/source-state FKs on immutable claims, and targeted indexes/CHECKs. Generate the EF migration and snapshot with the official SDK. Down vetoes any retained M6 mapping/result/claim/receipt, then preserves old v1 tables and hashes.
3. Host transaction: branch by mapping source schema; load all M5 facts under the shared serializable coordinator with stable locks; verify current Core scope, original invoice/document evidence, issued revision, policy and duplicate inventory; run the pure comparison; record blocked result or owner-backed claim atomically with audit/outbox/receipt. Original-key recovery verifies current actor/scope and typed retained response, without treating history as a new approval.
4. Procurement exposure owner: make one owner-only baseline after a read-only exhaustive inventory of the existing invoice/claim/credit/handoff/status/manual-payment graph. Capture exact old row IDs, active pointers, scope, source revision, amount/quantity and a complete-set digest; reject any unclassifiable row. Thereafter read every relevant append-only row and current pointer under the same serializable comparison transaction and stable exposure lock. Verify baseline plus later sequence has no gap, overlap or unexplained credit/release. Bind owner reference, set digest, sequence, current policy and short lease in the existing typed envelope. An empty current allocation table without that baseline remains unavailable. Finance posting is unaffected.
5. Private and release proof: genuine migration Up/Down/Up on a nonempty clone, full owner graph, finite roles, normal-cookie two-way/three-way/negative/recovery flows, original v1 row/digest preservation and no Finance posting. Production rollout is separately reviewed.

## Decisions before code that can reserve capacity

The owner is Procurement for billing-capacity control. Before claiming completeness, review the exact baseline migration/inventory contract against real old rows: `supplier_invoices`, all `invoice_match_allocations` and result/pointer rows, credit references, `finance_invoice_handoffs`, `finance_payment_status_refs`, and manual-payment records. Each must be classified as capacity-bearing, historical-only, or an explicit blocked ambiguity; no row is silently ignored. Define which approved return-effect record will reduce M5 acceptance, if such a route is included; M5d drafts do not. Choose the mapping payload source schema and physical FK shape so existing v1 response hashes remain byte-identical. These decisions do not block implementing the pure M5 source verifier and its negative tests, but they block turning on qualified claims.

### Proposed Procurement owner baseline and live set proof

The migration adds an immutable owner-baseline capture header, per-row inventory, and a narrow append-only command receipt for baseline Open/Decide. The header ID/version is the source of a shared Core approval case; a refreshed or stale capture creates a new header and case, preserving the old evidence. The receipt retains exact original response bytes and binds the baseline, Core case/decision, actor, key, request digest and company scope; it does not replace Core approval authority. The owning Procurement transaction reads every old invoice and matching allocation/result/exposure row, credit note and credit text reference, Finance handoff/status reference, and manual-payment request/decision in one serializable snapshot. It rejects any old active claim whose invoice pointer, result, mapping, PO/issued binding, supplier, currency or line set cannot be reconstructed. It records zero counts explicitly. A new company needs the same reviewed empty/current baseline before its first qualified comparison; feature enablement never creates one implicitly.

The proposed capture header stores `tenant_id`, `legal_entity_id`, schema/version and migration boundary, exact catalog manifest JSON/SHA, complete inventory SHA and count, captured UTC, initial exposure-state set digest and active-claim digest, maker identity, and Core case ID. Core owns reviewer identity and terminal decision; no caller-supplied approval flag appears on the header. A separate append-only inventory stores `(baseline_id, table_name, source_row_id)` uniquely with original row digest, immutable-field digest, initial classification, and optional invoice/order/source binding. This inventory distinguishes a recognized later Draft edit from an unexplained change to an old row. The third table journals only baseline Open/Decide responses. Its original-key GET requires the current authenticated actor and scoped read permission, but historical recovery does not demand that the former policy window remain current. The native migration must add exact tenant/company FKs, unique keys, bounded text/digest CHECKs and a Down veto for any retained baseline, inventory, receipt, principal mapping or claim before data-destructive DDL. The migration never manufactures an empty baseline on startup.

The independent reviewer is named by a published `INVOICE_OWNER_BASELINE_REVIEW` policy whose strict schema-1 document contains one Core principal ID. Opening requires a current company-wide, explicitly granted reviewer, a different maker, and one Core stage with one approval; this keeps the captured header and Core terminal decision unambiguous. M6A adds the policy key to its operational identity CHECK and policy lifecycle. Its normal API creation, review and publication still require the exact migrated schema, physical readiness and explicit Core action grants. A pure policy parser or Core opening plan alone cannot authorize a baseline or activate claims.

The manifest review starts from the actual Procurement tables `attachment_refs`, `supplier_invoices`, `supplier_invoice_lines`, `invoice_match_mapping_versions`, `invoice_match_results`, `invoice_match_allocations`, `invoice_match_exposure_states`, `invoice_exceptions`, `supplier_credit_note_refs`, `finance_invoice_handoffs`, `finance_payment_status_refs`, `manual_payment_requests`, `manual_payment_decisions`, `manual_payment_receipts`, `manual_payment_workflow_cases`, `manual_payment_core_decisions`, `manual_payment_date_observations`, `invoice_unit_review_sources`, `invoice_unit_review_assignments`, `invoice_unit_review_outcomes`, and `invoice_unit_review_receipts`. The reviewed migration must freeze the complete actual catalog list and scope rule before a baseline can be admitted; this source inventory is a starting checklist, not a claim that those tables currently contain zero or classifiable rows. The typed schema-2 Procurement owner envelope records the manifest SHA, per-table ID and row digests, baseline/current complete-set digests, disjoint active baseline/local claim digests, union digest, exposure sequence and lease. No adapter emits that envelope yet.

The current capture source reads these 21 tables itself under the shared serializable transaction and stores an immutable header plus exact row hashes. It reads retained allocation, invoice, result, mapping and per-PO exposure rows again through typed EF records in the same serializable snapshot and derives the active-claim digest; inconsistent links or sequence gaps stop capture. A complete reviewed inventory can establish `NoRetainedExposureForOrder` for a specific clean PO, while any source row linked to that PO prevents that conclusion and unexplained linked rows fail closed. A retained unlinked credit is checked from its unchanged captured row against the target supplier and currency; a changed or unclassifiable credit fails closed. An old manual-payment Draft with no effect can be classified as a mutable Draft, but later status, amount and receipt chains still need typed verification. Verified old allocation rows remain `BlockedAmbiguity` until the complete classifier and current transition owner are accepted. The Core case opens against that header ID/version and a separate actor must approve it. This is retained review evidence only. A resolved classifier, current-pointer/transition reconciler, owner envelope producer, genuine EF migration and native proof remain prerequisites for any qualified claim.

At comparison time the Procurement owner reads the complete relevant set in the **same serializable transaction and exposure lock** as the command. It checks every baseline row remains present or has a recognized retained transition, and checks every later claim has a contiguous exposure sequence and a current invoice active pointer. It includes all invoices linked by `PurchaseOrderId` or by any retained mapping, result or allocation, plus supplier/currency duplicates. An invoice with a Finance posting, payment, handoff or credit but no classifiable matching claim blocks new capacity on that invoice/PO; those records never silently release quantity. The live owner envelope binds baseline SHA, full current-set SHA, active-claim SHA, owner reference, scope, PO/issued/supplier/currency, policy digest, sequence and short validity window.

Baseline row hashes are capture evidence, not a permanent equality demand on mutable headers. The admission record freezes invoice identity, finalized or claim-bearing financial facts, old claim/result/allocation IDs and the old active-pointer classification. It also records the Draft invoice and manual-payment values at capture, then permits later edits, status, mapping revision or pointer changes only through a recognized typed command/receipt and current row-version transition under the owner lock. A post-baseline M6 mapping and claim on an old Draft invoice belongs to the **local post-baseline allocation partition** by allocation ID and exposure sequence, never to baseline merely because its invoice ID existed at capture. The producer compares the new current row with the frozen immutable fields or a complete permitted transition chain; unexplained financial-field changes, missing receipts, pointer jumps or allocation overlap block qualification. Tests must include an accepted old-Draft-to-new-M6-claim path and negative changed-amount/pointer/receipt cases.

`IInvoiceHistoricalExposureOwner.ReadAsync` currently has no transaction parameter. The installed comparison route receives its `ProcurementDbContext` only inside `ProcurementApprovalTransaction.ExecuteAsync`. The proposed Infrastructure factory binds that exact context to an owner instance within the callback; it retains the existing Application owner interface and verifies `Serializable`, the same connection/transaction, and the locked exposure row before any owner read. A separately injected DbContext or network call would produce a different snapshot and cannot issue `Complete=true`. The factory remains unregistered while the baseline table, admission procedure and physical readiness are pending.

The current `CompleteHistory` concatenates owner allocations with active local allocations. Internal owner implementation must define **one disjoint partition**. The recommended partition is baseline claims versus post-baseline claims, with exact baseline ID membership and an active-pointer check; the route loads only post-baseline local claims, and the owner returns only active baseline claims. The separate schema-2 owner envelope binds the reviewed baseline/Core case IDs, manifest/baseline/current-set hashes, historical/local/union allocation digests and exposure sequence. `CompleteHistory` recomputes the latter two digests from the actual disjoint inputs; this typed check does not establish that the current inventory was complete, which is the producer's responsibility. Any overlap, missing row, inactive pointer treated as active, unexplained credit, noncontiguous sequence, unknown legacy result or changed baseline digest blocks qualification. This is a Procurement billing-capacity proof, not an assertion about whether Finance has paid an invoice.

The current persistence guard permits a new active pointer only from null to a newly compared result, with new **Debit** allocations; it has no claim-release transition. This makes post-baseline active claims monotone. A later credit/release feature must introduce its own typed owner transition before it can change this partition or free capacity. Existing credit-note references and payment/handoff records remain conservative blockers where they make an old invoice's capacity unknowable.

The chosen mapping discriminator is `invoice_match_mapping_versions.source_schema_version` (nullable). A null value preserves the retained v1/v2 JSON and existing identity-schema interpretation; 3 identifies the new principal receiving payload while `identity_schema_version=2` still identifies the workerless Core actor. The new column and exact CHECK require a genuine migration before any stored v3 command. Unit-review source/retained-proof paths dispatch on this column and use an ephemeral document-link view only; comparison, claim construction, AP readiness and original-key response recovery still require separate v3 implementations and physical acceptance. Existing v1/v2 row bytes are not rewritten.

The separate additive M6B fact-link migration should add nullable `principal_receiving_source_state_id` and `principal_receiving_fact_id` to the existing allocation row, leaving its legacy receiving columns and v1/v2 payloads intact. Require both new IDs together and exclude them from the legacy receiving ID branch. Add a scoped composite FK from the allocation `(tenant_id, legal_entity_id, principal_receiving_fact_id, principal_receiving_source_state_id)` to a unique fact projection `(tenant_id, legal_entity_id, id, source_state_id)`, and another from `(tenant_id, legal_entity_id, principal_receiving_source_state_id, purchase_order_id, issued_version_id, purchase_order_line_id)` to a unique source-state projection with those exact six fields. Existing source-state primary scope and fact-to-draft-line FKs remain in force. The transactional loader must additionally prove `Acceptance`/`Accept` or `Certify`, exact draft-line/source/branch/issued-order bindings, accepted ledger quantity and amount, fact payload digest, and prior consumption before allocating. The two FKs prove stored identity and PO-line lineage; they do not by themselves prove acceptance or capacity. Source-schema-3 qualified claims stay disabled until M6B's genuine migration, native checks and complete loader have passed. M6A's accepted three-table baseline migration is unchanged.

The M6B source candidate now carries those two nullable model fields, EF composite relationships and a disjoint CHECK branch for the new pair. Its source3 allocation verifier binds every claim to the retained mapping line, exact accepted fact and full line set, then sums all provided active claims by fact against accepted quantity and net amount. Its enlisted loader replays each selected M5 source ledger, command receipts, bindings and retained policies from the same serializable Procurement context, using independently reconstructed issued-order sources supplied by the Host. This remains a source candidate until official EF generation and native FK/CHECK proof; the caller still must prove the input claim set and expected issued-order/Core sources are complete. A future M6B Down must veto retained nonnull principal fact/source allocation IDs before dropping either FK or column. No source3 claim route is enabled by these model changes.

The migration Down guard must reject any retained source-schema-3 mapping or result/review/receipt that refers to it, any admitted Procurement owner baseline/checkpoint, any new qualified principal allocation, and any `INVOICE_OWNER_BASELINE_REVIEW` policy or operational identity evidence. It must check those facts before dropping the discriminator or owner/claim tables or restoring the older policy-key CHECK. A rollback to the pre-M6 model cannot reinterpret a principal fact as a legacy acceptance or discard the owner evidence while leaving invoices and Core decisions behind.

## Migration checkpoint and release compatibility

The official offline EF scaffold has produced the three owner tables, the nullable mapping discriminator, and two CHECK replacements. Its generated migration ID was normalized one second after the future-dated M5d parent. The adopted migration places the retained-evidence guard as its first Down operation. The exported raw Down SQL predates that guard and is not an executable rollback artifact. A guarded SQL export, physical Up/Down/Up rehearsal, retained-data veto tests, and owning Host tests remain required before schema acceptance. The scaffold builds skipped analyzers under a bounded memory profile; the normal analyzer and full owning suite remain release gates.

M6 changes both the operational-policy identity CHECK and mapping-evidence CHECK. An older API image whose physical readiness expects the pre-M6 definitions may reject the upgraded schema even if the new owner tables are empty. Release planning must use a tested old/new image compatibility matrix or a compatible forward image, with a fresh backup and a separate schema decision. The earlier API-only rollback evidence applies to the unchanged pre-M6 model.
