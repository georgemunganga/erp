## Current branch scope

The deployed UI gate (`reference-ui/src/lib/ProcurementLiveGate.tsx:61-66` in UI `7cf8f55f`) allows “All permitted branches” on request, plan and contract list screens as well as master-data lists. P24 scope middleware (`backend/hrm-api/src/Mightyfin.Erp.Hrm.Api/ProcurementHostIntegration.cs:330-343,430-476,493-509` in product `b3e190ba`) recognizes a true All scope only for `GET` context/meta and Vendor/Item list, detail and export. On other routes, a valid All header retains the older concrete-branch behavior: a branch-confined user without a selected branch is assigned the first permitted branch in the selected company. A malformed or co-present All/location header is rejected. Thus an All request list can omit requests in other permitted branches: requests carry `BranchRef` and the list filters to the effective branch. Do not label that response as a complete company-wide list.

Plan and contract drafts are different: their current list queries are scoped to the Core owner subject and company, not to a branch column. They must not be turned into branch-owned records to repair the request-list gap. Verify the intended company-wide read contract per route and report the meaning of “All” honestly. Explicit selected-branch writes continue through existing P24 branch assignment and company checks; this inventory does not change their permission or command semantics. A company-wide view must never create a posting branch for a write.

## Release prerequisites

1. Reconcile the operational All contract by resource: branch-owned request/read aggregation across the caller's permitted branches; company-owned plan/contract read semantics; selected-branch creates and edits. Add finite scope, pagination, cross-company, workerless Core user and revocation cases before changing the UI promise or backend behavior.
2. For each held capability, establish exact model/migration and source ancestry, physical schema capture, finite grants, current Core authority, original evidence and actual API/owner/browser proof. Keep its server capability off until that route's gates pass. Use the [R0 schema gate](PROCUREMENT-FINISH-MILESTONES-20261025.md) before any P25+ deployment; do not treat private P38 schema rehearsal as production readiness.
3. Integrate accepted PRs in dependency order and verify the resulting combined source. Keep the P24 backport/release evidence distinct from later-model source, and record business UAT separately from technical deployment checks.
