The P23/P24 application and schema are deployed. It remains a draft, default-off change under [PR 33](https://github.com/georgemunganga/erp/pull/33). Its earlier source suites passed 1,253 domain and 586 host tests. Genuine private migration/recovery checks and a subsequent manual-evidence approval graph passed 31 actual HTTP requests, six replay/current-action checks and 35 raw storage denials, followed by independent read-only verification; see [the bounded acceptance record](release/PROC-PR-CORE-PRINCIPAL-APPROVAL.md#actual-private-manual-evidence-approval-and-storage-checkpoint). A fresh boundary run subsequently passed59 actual HTTP requests,18 finite-LOGIN privilege cases, five schema-protection defects, six current-account/selected-scope denials and actual authority revocation, followed by independent read-only review. Retained/current aliases, legacy compatibility and normal-authentication/browser integration/release gates remain pending. P25 has not been deployed; no real identity-provider or external Finance authority is claimed. Existing worker-based sourcing, ordering and receiving consumers require an explicitly tested bridge before using the new principal contracts.

**Finance ownership confirmed:** AP, accounting and payments belong to the future ERP Finance module, which has not been built. Procurement can store and validate its own records and prepare integration contracts. It must not manufacture budget reservations, posting IDs, payment status or a substitute finance ledger. Financial transitions remain unavailable until their owning service and acceptance evidence exist.

**Next sequence:** finish P25 command acknowledgement, durable UI recovery, the remaining privilege/alias/legacy matrix and real identity-provider/browser release gates; then implement and verify the sourcing → order → receipt bridges in dependency order. Keep invoice evidence/scanning, approval activation and all external hand-offs subject to their recorded prerequisites. Manus retains its focused task in [MANUS_HANDOFF.md](../../MANUS_HANDOFF.md).

## Historical baseline — 19 October 2026

The shared ERP host has authenticated, tenant/entity-scoped draft CRUD for suppliers, items, purchase requests, plans, categories, methods, contracts, sourcing events and buyer-owned purchase orders. Production runs the isolated Procurement schema through P18 and a Procurement-enabled API/UI; see [the live enablement record](PROC-OPS-02-LIVE-ENABLEMENT-20261019.md). The live workspace uses API-backed draft screens and empty workflow states for unsupported routes. Core supplies sign-in and organisation context; local sessions resolve configurable Procurement action grants from Core tenant roles. Supplier, item, catalog price and buying-method activation and buying-rule publication have independent review controls. A vendor approver with read and approve grants can inspect submitted or suspended suppliers in the selected legal entity without a manage grant; individual task assignments are not yet implemented. Submitted requests pin non-authoritative policy evidence to their current version; Finance can record an external reservation reference, but no ERP Finance reservation, delegated approval, purchase commitment, AP posting or payment is enabled. Vendor draft contacts, addresses and pending qualifications support reasoned, retained removal. Plan and sourcing revisions reject duplicate saved line IDs in their shared validators; plan, sourcing and contract draft changes record before/after business audit evidence. P18 adds retained line deactivation for buyer-owned purchase-order drafts; approval and issue remain gated. P17 adds a normalized supplier-invoice duplicate key; the first invoice slice only records structured manual intake as `Received`, with no source-document upload, matching, AP posting or payment. Read-only HRMS approver candidates are visible, but Core approval cases remain disabled. OIDC role mapping, binding workflow assignments, document upload, Finance and Inventory/Asset contracts require completion or verification.

**Company and currency decision:** New Procurement records use the company selected in Core. Its configured currency is shown in the Procurement context and fills a new supplier, request or plan draft when no currency is supplied. An existing draft keeps its stored currency during an edit that omits currency, even if the company default changes. The first company in the user's setup is Amizo Power; no company ID or currency is hard-coded into Procurement. This follows the distinction in [ERPNext Global Defaults](https://docs.frappe.io/erpnext/global-defaults) between a suggested company/default currency and a document's transaction currency. Spending thresholds, budget actions and supplier activation rules remain company-owned configuration decisions; draft CRUD does not imply approval.

## Implementation rule for every operation

1. Confirm the exact child operation in its 28-section spec: entry, state, actor, permission and data scope, guards, owner and failure path.
2. Add or verify schema constraints and a scoped API contract. Use explicit status transitions and optimistic version checks. Define external effects as durable outbox entries with stable idempotency keys.
3. Test allowed and denied actors, cross-tenant/entity object IDs, stale versions, duplicate requests, partial/exception flows and a disposable database migration. Do not let a browser record authorize a financial action.
4. Connect the existing UI screen to the API and verify loading, empty, error, conflict, success and permission-denied states. Keep each remaining demo screen visibly separate.
5. Record migration, review, backup/restore, staging UAT, monitoring and support evidence before production enablement.

## Contracts that block specific transitions

| Contract/decision | Blocks | Safe work that continues |
|---|---|---|
| Procurement thresholds, supplier diligence and delegated authority | Activation, submit/approve, RFx publish/award, PO issue | Draft validation, list/detail/edit, policy editor and test fixtures |
| Finance budget reservation and AP/payment callback | Budget approval, PO commitment, AP handoff and payment status | Internal estimates, invoice capture, exception drafting and contract tests |
| Shared document scanning/access and external supplier identity | Evidence-based approval and portal publication | Internal records and attachment-reference contracts |
| Inventory/Asset item mapping and receipt tolerances | Stock/asset handoff and over-receipt | Receipt draft/inspection evidence and integration outbox contracts |
| Production backup, migration review, threat model, independent security review and UAT | Production activation | Source implementation and disposable/staging verification |

## 19 October 2026 checkpoint

Supplier proposal, review and activation; reasoned category/item and buying-method activation; independently reviewed catalog price publication/withdrawal; request submission to `PendingPolicyAndBudget`; and an append-only Finance budget decision API have reached production through v18. P11 links a request line to the selected published catalog price/version and revalidates availability at submission. P12 records buying-rule review/publication evidence; P13 pins a line-by-line rule result to each submitted request version. The Finance budget result is evidence from a designated reviewer, not an implemented Finance reservation integration. A rule match is not approval. Shared workflow approvals, sourcing awards, purchase orders, receiving, invoice matching, AP hand-off and the supplier portal remain future waves. The following register preserves the earlier 18 October baseline for traceability.
