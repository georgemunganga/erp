# Core outbox publisher startup boundary

**Status:** Source-only prerequisite; actual build, runtime-role, schema and publisher tests are pending. This is a process ownership decision under [GW-ENG-STD-001](../engineering/GW-ENG-STD-001.md), not a new business feature.

The HRM host has three mutually exclusive startup modes. `--apply-migrations-only` is the dedicated schema-owner command and retains the existing `CoreSchemaStartup.MayApplyMigrations` behavior. Ordinary API startup retains its existing development/configuration behavior and local identity bootstrap. `--run-outbox-publisher` is a worker process: it always calls `CoreSchemaStartup.EnsureAsync` in **validate-only** mode, even in Development or with `ERP:Database:MigrateOnStartup=true`, and never calls `LocalIdentityBootstrap.EnsureAsync`.

Both CLI flags together, or a malformed flag in the reserved `--run-*` / `--apply-*` namespaces, fail before configuring or opening a database. These namespaces are reserved for operating commands, so an unknown command such as `--run-outbux-publisher` also fails closed. Only the exact case-sensitive mode flags are accepted; unrelated host options remain available. The publisher still requires an up-to-date Core schema; pending or unscaffolded migrations fail startup. The change does not authorize DDL, a local-admin seed, a new role or an alternate migration owner for the publisher.

`CoreHostStartupPolicy` owns the pure mode/authority decision. `Program.cs` applies it before schema readiness and places the publisher exit before the identity-bootstrap call. `CoreSchemaStartup` remains the shared model/history check; LocalIdentityBootstrap remains an ordinary API-only operation. This source change is a prerequisite for separate finite API/publisher database credentials. It does **not** establish that those credentials or production privilege separation are already deployed.

Acceptance requires compiled policy matrix tests for Development/config true and false, both mixed-flag orders, the unchanged migration-owner and ordinary API paths, plus a private startup check with separate finite roles. The private check must show publisher schema validation without DDL and without a new local admin, owner-only migration, and ordinary API behavior against its scoped database. No database operation is executed by this document.

## Nonempty cross-tenant claim follow-up

The earlier private publisher check had an empty outbox. A nonempty global claim can contain rows from several tenants: `IgnoreQueryFilters()` permits the read, while Core's `FillTenantIds()` still rejects a modified row whose tenant differs from the publisher's default context. The save interceptor also writes an audit entry, so the publisher must bind **both** the row update and its audit to the tenant stored on the locked outbox row. Event payload fields never supply this authority.

The bounded source repair uses a publisher-process-only tenant accessor. It starts unbound, saves one database-loaded claimed row at a time inside the existing claim transaction, clears the binding before the next row, and repeats the binding for the database-loaded completion row. Ordinary API principal scoping, `FillTenantIds()`, query filters and audit immutability remain unchanged. The finite publisher role needs outbox SELECT, named operational UPDATE columns and audit INSERT; it must have no Core identity writes or schema authority. This grant is a proposed private-role probe input, not a production role change.

Acceptance remains open until current-source tests and a private, nonempty two-tenant PostgreSQL probe pass. The probe must first prove the original eligible queue is empty, seed only synthetic rows, claim and acknowledge both tenants under the finite role, retain original-row hashes, then exercise the genuine publisher process with no-template synthetic events in a network-isolated container. A clean stop and tenant-correct outbox/audit rows prove processing; this does not prove external notification delivery or production activation.
