# P25 legacy worker bridge — source-only

`P25_HTTP_VERIFY_LEGACY_WORKER_BRIDGE=1` is a separate opt-in on a newly created,
empty private P25 database. It is exclusive of every other optional P25 probe
cohort and local-cookie serve. Run it with the existing exact private socket,
finite record/execution roles and new protected result path. No SDK, database
or browser acceptance is claimed by this source commit.

P25 widened the old worker-only Finance and spending-authority CHECKs. The
strict P21 inspectors correctly reject those new physical definitions. For
established worker workflows, the normal host now registers the concrete P25
inspector independently of the principal interface. A false
`PrincipalExecutionEnabled` setting still resolves the principal interface to
Unavailable and captures **no new principal1 request or authority2 evidence**.
The old P21 exact checker runs first; only if it fails may the concrete P25
inspector validate the actual complete migration, finite SQL role, exact
columns/constraints/indexes and Core access. Pre-P25 databases keep their old
strict path. This is not a true-ready stub, substring check or role grant.

The cohort creates exactly three active synthetic Core workers, each uniquely
linked to a separate Maker, Checker and Approver account in the private
company/branch. Its private roles give Maker authority-configuration and
Checker authority-review actions; the Approver retains the existing approval
actions and the legacy `procurement_manager` role marker. Other P25 probe
modes still create no workers or additional role actions.

With the principal option **false**, mapped APIs create/submit/activate a
worker1 spending authority, publish an independently reviewed policy and
category, and create/submit a worker-linked request. Owning reload requires
original `requester_identity_schema_version=0` and null principal digest; the
request is never backfilled. A second normal host with the option still **false**
uses actual P25 readiness to record checker1 and execute the old worker
resolver/pinning through the mapped budget, readiness, Open and independent
Decide APIs. Owner reload requires the same exact three workers, authority1
Created/Submitted/Activated lineage, checker1, submission2/assignment1,
approved Core case/decision, two command receipts, exact 2 × 5.1234 line and no AP/payment facts.
The manual Finance reference is explicitly synthetic, never an external
reservation or ledger confirmation. Principal1 and workerless operation
remain separate accepted P25 cohorts; this test does not establish full
module completion, native IdP or production activation.
